# Upstream bugs

Bugs found in crates Graphix depends on, for fixing upstream. Graphix
works around one only when it breaks Graphix's own operation; each entry
says whether it does and where. When a fix lands upstream, bump the
dependency, delete the workaround and its entry.

Each entry: the crate and version, what is wrong, how to reproduce it,
the state of a fix, and Graphix's side.

## cranelift-jit 0.137 / region 3.0.2: the arena commits its whole reservation on Windows

- **Bug.** `ArenaMemoryProvider::new_with_size` reserves through
  `region::alloc`, which on Windows calls `VirtualAlloc` with
  `MEM_COMMIT | MEM_RESERVE` (region `src/os/windows.rs`). Each arena
  charges its full size against the commit limit (RAM plus page file),
  where on Linux it is address space only. cranelift-jit's own comment
  says so and points at region-rs PR #34.
- **Repro.** On Windows 11, 64 `ArenaMemoryProvider::new_with_size(256 <<
  20)` raise the process's `PrivateUsage` by 16,416 MB; the same 64 of
  Graphix's arena raise it by 0 MB. Where the page file cannot grow, the
  reservations fail.
- **Upstream fix.** region's Windows `alloc` reserving only (region-rs
  PR #34), or cranelift-jit's arena reserving with `MEM_RESERVE` and
  committing each segment as it allocates.
- **Graphix's side.** Worked around (a few fusing runtimes exhaust the
  page file and run unfused): `fusion/emit/arena.rs` is Graphix's own
  `JITMemoryProvider`, reserving the arena and committing a page run per
  allocation on every host. Not reported.

## calamine 0.34: the ods and xls readers are dense over a sheet's used area

- **Bug.** calamine reads every ods table when the workbook opens, as a
  dense range over the area its cells span with repeats expanded. A few KB
  of `content.xml` whose rows end in a cell far to the right, or a cell at
  A1 plus one far corner, allocate tens of millions of cells (32.7M from a
  2.6 KB file). The BIFF xls reader also builds every sheet at open with
  `Range::from_sparse`, allocating the cells' whole bounding box. A 5.6 KB
  xls with cells at A1 and (65535, 65535) requests 2^32 cells (128 GiB).
  Even listing sheet names opens these ranges. xlsx and xlsb have sparse
  cell readers; ods and xls have none.
- **Repro.** `stdlib/graphix-package-xls/src/lib.rs` tests
  `ods_refuses_many_far_rows`, `ods_refuses_a_far_corner`,
  `ods_refuses_far_rows_valued_by_any_attribute` build such files.
  `design/review-2026-10-26/repro/small-pkgs-xls-dense-oom.sh` constructs
  the xls case. Running its generated input through `xls::sheets` with
  an 8 GiB address-space limit aborts requesting 137438953472 bytes.
  The bounded pin `xls_sparse_cells_span_the_full_bounding_box` opens the same
  5.6 KB layout with its far cell at (255, 255). It checks the 256×256
  range dimensions and the two populated cells, not allocated storage or
  whether allocation happens at open. The allocation claim is supported by
  the reader implementation and the memory-limited probe above.
  `tests/data/sparse.xls` was generated by
  that probe's `mkxls.py` with arguments `1 255 255`.
- **Upstream fix.** Sparse ods and xls cell readers like xlsx's
  `worksheet_cells_reader`, or a caller-set cell limit at open.
- **Graphix's side.** Worked around (a crafted file OOM-kills the
  runtime): `check_ods` streams `content.xml` before calamine opens it and
  refuses where the tables together pass `MAX_CELLS`, mirroring by hand
  which attributes calamine reads a value from (`ODS_VALUE_ATTRIBUTES`),
  so it must follow calamine's parser. There is no xls preflight limit:
  `MAX_CELLS` is checked after calamine allocates the sheet. This limitation
  is accepted and documented in the xls book/API; untrusted xls input
  needs an externally enforced memory limit. Not reported.

## calamine 0.34: the xlsx open reserves the declared shared string count

- **Bug.** `Xlsx::read_shared_strings` reserves its strings vector to the
  `sst` element's `uniqueCount` attribute, unchecked, when the workbook
  opens. A 1 KB xlsx declaring `uniqueCount="100000000000"` asks for
  2.4 TB, and the failed allocation aborts the process. It also builds a
  string for every `si` element it meets, so a few MB of `<si/>` (5 bytes
  each, deflated about 1000:1) grow the vector to tens of GB.
- **Repro.** `stdlib/graphix-package-xls/src/lib.rs` tests
  `xlsx_refuses_an_overstated_string_count` and
  `xlsx_refuses_more_strings_than_the_cell_bound` build such files.
- **Upstream fix.** Cap the reservation (by the part's size, or a fixed
  bound), or treat the count as a hint only; and a limit on the strings
  an open builds.
- **Graphix's side.** Worked around (a crafted file aborts the runtime):
  `check_shared_strings` streams every zip entry calamine would take for
  `xl/sharedStrings.xml` before it opens, counts every `si` element after
  the `sst` element's start (calamine builds a string for each one its
  loop meets, nested or past an `</sst>` inside a string, before any cell
  bound applies), and refuses more of them than `MAX_CELLS`, a count
  declared or not, and a declared count past them; it mirrors how
  calamine finds the part and reads the attribute. Not reported.

## crossterm 0.29: an EventStream's shutdown is one wake any poller may take

- **Bug.** A polled `EventStream` sends its background thread a task, and
  the thread waits in `poll_internal(None)`, holding the global event
  reader's lock for as long as no event comes. The stream's drop stops the
  thread only by waking the reader's one shared waker, and whichever poll
  runs next takes that wake. When it is another poll (the line editor's,
  or any `event::poll`), the dropped stream's thread, if it had not yet
  reached its poll, then holds the lock forever: the next
  `EventStream::new()` blocks on the lock for good, and
  `cursor::position()` fails after 2 s with "The cursor position could
  not be read within a normal duration" (the thread swallows the answer
  into its skipped events). When no poll is in flight at the drop, the
  wake stays pending and the next `poll_internal` anywhere returns at
  once, as if it timed out, failing `cursor::position()` at once.
- **Repro.** In a PTY: create an `EventStream`, start a 2 s
  `event::poll` on another thread, poll the stream once, drop it; the
  poll returns at once, and a second `EventStream::new()` never returns.
  In the REPL at a terminal, TUI displays that end at once
  (`{ tui::exit(null); tui::text::text(&"bye") }`) hung the shell at a
  later display's start, one run in ten under load.
- **Upstream fix.** The stream's own thread should be stopped by
  something only it takes, and should not hold the reader's lock across
  an unbounded poll.
- **Graphix's side.** Worked around (the REPL hung): no `EventStream`.
  The TUI display reads events on a thread of its own that polls with a
  50 ms bound and is stopped and waited for when the display gives the
  terminal back (`stdlib/graphix-package-tui/src/lib.rs` `Events`); the
  workspace builds crossterm without `event-stream`. Pins:
  `stdlib/graphix-package-tui/src/test/terminal_test.rs`
  `a_display_ending_beside_another_reader_leaves_the_terminal`,
  `graphix-shell/tests/shell/repl_interrupt.rs`
  `tui_displays_ending_at_once_give_the_prompt_back`. Not reported.

## handlebars-rust 6.4: template depth recurses without a bound

- **Bug.** Parsing, cloning, rendering and dropping a template recurse
  once per nesting level, and an `{{else if ..}}` chain nests one level
  per link (`HelperTemplate::insert_inverse_node`, template.rs). A
  template of a few thousand nested blocks or chain links overflows the
  stack and aborts the process.
- **Repro.** `stdlib/graphix-tests/src/lib_tests/hbs.rs`
  `hbs_block_nesting_refused`: `{{#if a}}x` + 5000 × `{{else if a}}y` +
  `{{/if}}`.
- **Upstream fix.** An iterative template walk, or a depth limit the
  registry enforces at parse with an error.
- **Graphix's side.** Worked around (a template from data aborts the
  process): `compile` in `stdlib/graphix-package-hbs/src/lib.rs` parses,
  builds and drops a template on a stack grown by the brackets in its text
  (stacker), then refuses blocks and subexpressions nesting past
  `MAX_BLOCK_DEPTH`, measured on the template handlebars built. Not
  reported.

## handlebars-rust 6.4 / pest 2.9: compiling a template is quadratic in its length

- **Bug.** `Template::compile` records where each element starts through
  pest's `Position::line_col`, which counts lines from the start of the
  text at every call, so a compile costs the text's length times its
  elements: a template of a few thousand blocks (tens of KB) takes seconds.
  A profile of the whole test suite (`cargo xtest`, 2026-11) spends 7% of
  its CPU there, nearly all in `hbs_block_nesting_refused` and
  `hbs_text_nesting_refused`'s 5000-level templates.
- **Repro.** `hbs::render` of `{{#if a}}` × 5000, `x`, `{{/if}}` × 5000;
  `perf record` shows `pest::position::Position::line_col` under
  `handlebars::template::Template::compile2`.
- **Upstream fix.** Track line and column as the parse advances (or index
  the line starts once) instead of rescanning from the start.
- **Graphix's side.** Worked around where it met the depth bound:
  `surely_deeper` in `stdlib/graphix-package-hbs/src/lib.rs` reads the text
  by the grammar and refuses one surely nested past `MAX_BLOCK_DEPTH` before
  handlebars compiles it (it gives up on what it cannot read, and the
  compile measures). A long template within the bound still compiles in
  quadratic time; a compiled template is cached per thread (`FastMemo`).
  Not reported.

## sled 0.34.7: a dropped reservation never wakes its subscriber

- **Bug.** A write that changes nothing drops its `ReservedBroadcast`
  without waking the subscribers it reserved, and `Subscriber::
  next_timeout` saves the dropped oneshot back, so it answers
  `Disconnected` on every later call. A watched tree then wedges writers
  or loses events.
- **Upstream fix.** Prepared, not submitted: `~/proj/sled`, branch
  `subscriber-dropped-reservations` (df42b243 on v0.34.7): a dropped
  reservation wakes its subscribers, `next_timeout` skips one and reports
  a timeout as `Timeout`, two tests. sled's main is the 1.0 rewrite with
  no subscribers, so the PR targets a 0.34 branch (`origin/tyler_0.34.7`
  is v0.34.7).
- **Graphix's side.** No longer reached: the db package keeps its own
  watches (`stdlib/graphix-package-db/src/watch.rs`) and uses no sled
  subscriber.

## sled 0.34.7: collections are created outside transactions

## sled 0.34.7: import into a database holding only a tree's meta entry panics

- **Graphix's side.** Worked around: the db package validates an import

## iced_widget 0.14: rich text does not redraw when the hovered link changes

## netidx (ours): a stream replay reaches every channel of a subscription

- **Bug.** `subscriber/connection.rs::handle_connect_stream` pushes a
  joining channel's `BEGIN_WITH_LAST` replay into the stream batch, and
  `process_updates_batch` broadcasts it to every channel on the
  subscription: existing readers fire again, and several registrations
  in one batch replay duplicates.
- **Upstream fix.** Target the replay at the joining channel, in stream
  order.
- **Graphix's side.** `sys::net` keeps one shared channel per
  subscription and replays `last` itself, which is racy: a late second
  reader of a busy path can see a value twice or out of order (Eric's
  open CRs sys-net-01 and x-concurrency-07 in
  `stdlib/graphix-package-sys/src/netstate.rs`).

## netidx (ours): a directory's change number can repeat after a change

- **Bug.** The resolver answers `GetChangeNr` with the sum of each
  shard's counter for the path (`resolver_server/shard_store.rs`), and a
  shard drops its counter once it holds nothing under the path
  (`resolver_server/store.rs::remove_parents`); a later add starts it
  again at 1. A change that empties one shard's part of a directory and
  adds to another's can leave the sum where it was, and
  `ResolverRead::check_changed` then reports no change.
- **Repro.** Publish `/d/a`, check the change number, then unpublish
  `/d/a` and publish `/d/b` where the two paths hash to different shards:
  the number is 1 before and after.
- **Upstream fix.** A shard keeps the counter of a path it held, or the
  resolver bumps a counter of its own at every write under the path.
- **Graphix's side.** Worked around (a polled listing kept answering a
  listing that had changed: the TUI browser went on showing columns a
  table had lost): `sys::net::list` and `list_table` list at every tick
  and answer a listing only when it differs from the last they answered
  (`stdlib/graphix-package-sys/src/netstate.rs`), a listing per tick
  where a change number was. Pin
  `lib_tests::net::net_list_sees_a_replaced_path`. Not reported.

## netidx (ours): a Dval that joins its path's subscription hears it under another id

- **Bug.** A `Dval` mints its `SubId` when it is made
  (`subscriber/mod.rs::subscribe_internal`), and a connection tags a
  subscription's events with the id of the request that made its `Val`.
  A `Dval` made for a path whose subscribe is in flight for one dropped
  meanwhile joins that subscribe (`St::WaitingOther`) and holds its
  `Val`, but every event on its channels, the `BEGIN_WITH_LAST` replay
  included, carries the dropped one's id, so a consumer that routes by
  `SubId` drops them all. The subscribe is in flight until the
  resubscription task takes its result, after the connection has already
  sent the first value, so a consumer that drops a `Dval` as it shows its
  first value hits this. So does a `Dval` made beside a live non-durable
  `Val` of its path, and one whose path aliases another's published value
  (the alias arm of `From::Subscribed` in `subscriber/connection.rs`).
- **Repro.** Hold a subscribe at a default publisher, drop the `Dval`
  that asked, subscribe the path again with a channel, then answer: the
  channel gets every event under the dropped `Dval`'s id and none under
  the new one's (3 of 3 runs). A `Dval` made while a non-durable `Val`
  of its path lives has another id than the `Val`, whose id its events
  carry (3 of 3).
- **Upstream fix.** A new `Dval` takes the id of its path's subscription,
  live or pending: `SubStatus::Pending` carries the id minted when the
  subscribe starts, which the request then uses. The alias case needs an
  id per registered channel.
- **Graphix's side.** Worked around in part (a hang: a cell or a sort
  never got its value). The data table routes its one channel's events by
  `SubId` (`spawn_dispatch_task` in
  `stdlib/graphix-package-gui/src/widgets/data_table/subscriptions.rs`),
  so it keeps a subscription whose role changes live through the
  reconcile and never drops a path and subscribes it again in one
  (`SharedCellsInner::reconcile`). Pin
  `data_table_test::a_live_column_flipping_types_keeps_its_subscription`.
  A path one reconcile drops while its subscribe is in flight and a later
  one wants again still hangs: `sort_by_change_resorts_offscreen_rows`
  (rows scrolled away by a direction flip, then sorted by their other
  column) failed 1 of 10 suite runs under load. `sys::net` gives each
  reader a channel of its own and reads no tag.
- **Fixed in netidx c0c47111** (the upstream fix above, with tests
  `a_dval_replacing_one_dropped_mid_subscribe_gets_its_updates` and
  `a_dval_beside_a_live_val_gets_its_updates`): the data table suite
  passed 70 of 70 runs on it where it failed 6 of 115 before. The alias
  case stands. The data table's reconcile keeps its live subscriptions
  anyway (no resubscribe for a changed role).

- **Bug.** `iced_core::layout::flex` adds a row's or column's

## ratatui-core 0.1.2: Buffer::merge indexes cells in u16

- **Bug.** `Buffer::merge` moves the receiver's cells to their place in

## ratatui-widgets 0.3.2: Chart and BarChart add text widths in u16

## line-clipping 0.3.7 / ratatui-widgets 0.3.2: finite line clipping overflows

- **Effect.** The Cohen–Sutherland clipper multiplies coordinate differences
  before dividing. Finite endpoints can produce infinity or NaN, drawing the
  wrong cells. Rejecting overflowing differences also drops crossing segments.
- **Repro.** `design/review-2026-10-26/repro/tui-widgets-canvas-line-clip.sh`;
  `canvas::tests::enormous_canvas_lines_match_their_visible_segments` pins the
  rendered result without a terminal or sockets.
- **Graphix workaround.** Clip from the original endpoints with power-of-two
  scaling and a compensated determinant. Canvas lines clip to the window. Chart
  lines clip to a box padded by one axis span on each side and join disconnected
  pieces along its perimeter, outside the visible window. One dataset per series
  keeps all its Braille dots in one canvas layer. Separate layers cost a full-area
  allocation and traversal and replace earlier cells instead of merging dots.
  Enormous chart axes and all their series scale down by powers of two before
  clipping, keeping ratatui's remaining products finite.
- **Pins.** `clip::tests::asymmetric_segments_keep_their_slope`,
  `chart::tests::reentering_line_preserves_braille_dots`,
  `chart::tests::perimeter_joins_never_enter_the_window`,
  `test::panic_test::enormous_chart_axes_preserve_each_graph_type`, and
  `chart::tests::reentering_line_uses_one_layer` (also prints render timings).
- **Status.** Not reported upstream.

## serde_json 1.0.154 (arbitrary_precision): an object keyed by the number token reads as a number

- **Bug.** Under `arbitrary_precision`, which graphix-package-json turns on
  to read numbers exactly, serde_json hands a visitor a number as a map of
  one entry keyed `$serde_json::private::Number`, the number's text its
  value. An object in the input with that key reaches the visitor the same
  way, so no reader tells the two apart, and json's reader takes such an
  object for a number (documented in its gxi).
- **Repro.** `let v: Map<string, i64> = {"$serde_json::private::Number" =>
  5}`: `json::write_str(v)` writes `{"$serde_json::private::Number":5}`,
  and `json::read` of it into `Map<string, i64>` fails ``JsonErr("invalid
  type: integer `5`, expected a string at line 1 column 33")``; the key over
  the string `"42"` reads back as the number 42, an `InvalidCast` into
  `Map<string, string>`. On main a map under `Any` writes as an object too,
  so `Map<string, Any>` holding that map reads back, silently, as `{"x" =>
  42}`; under the map-key ruling (lane B round 6) a map under `Any` writes
  its pairs and only a `string`-keyed map writes the key, whose read is
  refused. TOML reads the key back. Probes
  `~/ptmp/cr29/scratch/review-r6/B-r3-1/rt/serde_key.gx`,
  `~/ptmp/cr29/scratch/r6-B/f3/serde_key2.gx`, `serde_key3.gx`.
- **Upstream fix.** A number passed to a visitor through a channel a JSON
  object cannot reach (serde's private `Content`, or a token no object can
  spell). Not reported.
- **Graphix's side.** Not worked around: with the map-key ruling what is
  left is a refused read, no wrong answer. The json writer should still
  refuse the key (in a `string`-keyed map, the only place a program writes
  it; no struct field or abstract type's name spells it), as it refuses two
  keys that write as one: `JsonData` promises the reader takes back what
  the writer writes, and this value it cannot. TOML needs nothing.

## tokio 1.54.1: an unbounded send racing the receiver's drop keeps its message

- **Bug.** `UnboundedSender::send` counts the message in the channel's
  semaphore, which fails once the receiver is closed, and then pushes it
  (`sync/mpsc/unbounded.rs` `send`, `inc_num_messages`). `Rx::drop` closes
  the channel and drains what the list holds (`sync/mpsc/chan.rs`). A send
  that passed the open check before the close and pushes after the drain
  returns `Ok`, but its message is neither received nor dropped: it stays
  in the channel until the last sender drops. A message holding a
  `oneshot::Sender` leaves its receiver waiting that long, forever where a
  sender outlives the wait.
- **Repro.** `graphix-rt/tests/rt/stop_race.rs`
  `a_request_racing_the_stop_is_answered`: eight callers loop
  `GXHandle::get_env` while the runtime is aborted, 3000 trials. Against a
  run loop that drops its receiver it hung in 3 of 4 runs at 1000 trials.
- **Upstream fix.** `Rx::drop` waiting out the sends its semaphore still
  counts, as `recv` after `close` does, or a send that finds the receiver
  gone after its push draining the list itself. Not reported.
- **Graphix's side.** Worked around (a shell whose runtime stopped could
  hang forever: a request sent as the run loop ended was never answered):
  `GX::run` borrows the request receiver, and the runtime's task
  (`GXConfig::start`) then closes it and receives until it is empty, which
  waits for every send that passed the open check, so each request is
  dropped and its caller answered with the stop.

## wl-clipboard-rs 0.9.3 (through arboard 3.7.0): a paste waits on the owner with no timeout

- **Bug.** Under Wayland's data-control protocol, arboard reads the clipboard
  through wl-clipboard-rs, which reads the owner's pipe with `read_to_end` and
  no deadline. An owner that neither writes nor closes the pipe blocks the
  read for good. arboard's X11 path gives up after 4 s.
- **Repro.** Not run; found by reading (review r9 of gui-core-02). A client
  that offers text and never answers the transfer would show it.
- **Upstream fix.** A deadline on the read in wl-clipboard-rs, or arboard
  bounding its Wayland read as it bounds the X11 one.
- **Graphix's side.** Not worked around: no such owner has been seen. If one
  turns up, a paste in the GUI blocks the window's thread while it holds the
  process's one clipboard (`gui::clipboard`), and a `gui::clipboard` builtin's
  call never answers.
